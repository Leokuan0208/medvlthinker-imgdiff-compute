## 2. Code defects found and fixed

**2.1 A live currency bug producing up to 12.4× wrong numbers.** `head_temperature_sweep.py:108` read `d["oks"]` — exact match, computed at generation time — for its one-sample term, while greedy, head and oracle on the same rows are 32B-judge labels.

| benchmark | published penalty | correct | error |
|---|---:|---:|---|
| gemex | +0.2288 | +0.0185 | **12.4×** |
| omnimed | +0.1237 | +0.0149 | 8.3× |
| slake | −0.0093 | +0.0107 | **sign flip** |

I fixed exactly this in `decomposition_report.py` in August and **never propagated it back** — the failure mode CLAUDE.md §9.6 names. Fixed by *deleting* the duplicate: after the currency fix the two scripts still disagreed on all 8 benchmarks, because the sweep fell back to a distinct-answer mean where the reference skipped the question. One quantity, two implementations, two answers is the bug class. `decomposition_2026-08-24.json` is now the single source of truth; the sweep owns head-vs-greedy across temperature.

**2.2 A degenerate cluster bootstrap.** `mixed_temperature_pool.py:152,154` passed unique question ids as the cluster key, so every group was a singleton and the bootstrap collapsed to i.i.d. while reading as clustered. Eight WIN/LOSS verdicts were published on it. Now clusters by `img_md5`.

**2.3 A contamination check that hashed nothing.** `build_vqamed_cell.py` globbed `*.jpg`; every VQA-RAD image on disk is `.png` (2,249 png, 0 jpg). That arm printed "0 VQA-RAD images" and is the root cause of the 19 MedPix images shared with `vqa_rad_open_train`. Now extension-agnostic.

**2.4 Three cell builders never audited the training pool** — only the eval metas. A new cell could silently share images with the probe's own training data, which is what happened. All three now include it.

**2.5 An incomplete judge file that looked finished.** `ckpt_kvasir_x1_open_lingshu7bT10_sc8_scexploded` was exploded **4 minutes before its dump finished** and covered 8,064 of 10,121 questions, so every T=1.0 kvasir_x1 number was on 79.7% of the benchmark. Fixed with a **general planner rule** that re-explodes any dump whose judged count is short of it — it immediately caught this and PathVQA. Both now at full coverage.

## 3. PathVQA was reported on 1,500 of 3,357 questions

`run_openvqa.py:158` does `items = items[:A.n]`, and the T=0.7 sc8 and greedy runs were launched with a cap. Every other tag on that benchmark held all 3,357. Nothing downstream records how many questions the dataset *had*, so it was invisible.

**Not a random subsample.** The cut is a clean idx prefix (0–2854 kept), and the omitted half is **harder**: exact-match 0.2645 vs 0.3132, gold 2.65 vs 2.36 words, 3.37 vs 3.15 distinct candidates. Every PathVQA number in the project sits on an easier-than-average prefix, and PathVQA is load-bearing.

**Status:** generation and judging are complete at 3,357; hidden-state extraction is running. The impact will be **measured** before deciding whether the shared shard caches are worth rebuilding.

## 4. The 19 MedPix images — measured, not estimated

The effect lived in a **code comment** as "−0.0259 → −0.0261", which is an estimate where rule 7 requires a measurement. Now measured (`vqamed_contamination_2026-09-12.json`): 19 of 3,663 questions (0.519%), delta moves −0.0259 → **−0.0261** (−0.00014). Immaterial, and demonstrably so — those questions score **0.0000 for both verifier and greedy** (oracle 0.1579), so the overlap could not have inflated anything.

**The cell was NOT rebuilt.** Rebuilding would invalidate and require regenerating every VQA-Med number to move a measured −0.00014. The builder is fixed so no future cell repeats it. Any doc saying the images were "removed" is wrong — they are still in the cell, and the reason is recorded here.

## 5b. What an adversarial re-check of these fixes then found (2026-09-13)

The fixes above were re-verified by independent skeptics prompted to prove each one had NOT worked.
**Seven passed. Two failed**, and both failures were mine:

**The PathVQA backfill landed but did not propagate.** The data is right — 3,357 generated, judged
and extracted — but it went into `generator_eval_pathvqa_full` at layers 18/20/21/22, while every
analysis reads `generator_eval_<cell><SUF>` at layers 7/14/21/28. Different stem, different layers,
so **not one reported number moved**. Worse: `head_temperature_2026-08-22.json` was regenerated
*after* the backfill and is now internally inconsistent — PathVQA reads **n=1,500 at T=0.7** and
**n=3,357 at 0.2/0.4/1.0**, so `best_T` for that benchmark compares different question sets. A
re-extraction into the canonical stem at the canonical layers is queued.

**Two document corrections silently missed, and one was corrected against a deleted version.**
"4,316 distinct golds" and "confidence 0.693" both **span a line break** in the markdown, so exact
string replacement matched neither — the first pass reported six corrections applied and did not
notice two had not. Separately, "6 of 8" was corrected against the `mixed_temperature` artifact that
**the same commit then regenerated**; the current artifact says **7 of 8** (PathVQA flipped when its
n went 1,500 → 3,357). All three are now fixed with line-break-tolerant patterns and re-derived
against the artifacts on disk.

Still outstanding from that re-check, recorded rather than silently carried: the HTML rundown, the
